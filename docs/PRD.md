## 1. 背景与机会

### 1.1 问题

旅行者在「种草 → 结构化行程 → 可执行 → 可协作」链路上，常见痛点包括：

- **纯对话类 AI**（如豆包）：出稿快，但**事实与时刻**易错，难以形成可版本化的行程资产，也缺少与地图/同行者的结构化协作。  
- **攻略导入类**（如圆周旅迹）：贴合国内内容习惯，但**自动动线质量**与**可验证性**常不足，**预订闭环**弱。  
- **海外 AI 规划**（如 Mindtrip、Travo、Plantrip）：在可视化、导出、部分预订等各有长板，但**国内 POI/内容源/支付习惯**未必匹配，且普遍存在**门票与时刻表**类误差。

### 1.2 机会假设（待验证）

提供一款 **私人 AI 旅行规划助手**：在长期对话中 **个性化沉淀用户偏好**，并以 **可核验的航班 / 车次 / 酒店数据**（对接权威或授权数据源，而非仅靠模型臆测）支撑结构化行程；让用户少踩通用聊天机器人常见的 **事实性错误**。

---

## 2. 产品愿景与目标

### 2.1 产品愿景（一句话）

TravelPlan 要成为 **更懂你的私人 AI 旅行规划助手**：通过 **长期、多轮的沟通** 理解并记住你的旅行偏好，逐步产出 **更贴合你心意** 的方案；同时在 **航班、列车、酒店** 等关键事实上 **对齐可验证数据源**，显著减少通用对话机器人常见的「瞎编班次与房源」问题。

### 2.2 核心卖点

#### 卖点一：个性化 —「越聊越懂你」

- **私人助手心智**：区别于「一问一答、单次生成攻略」，产品鼓励用户与助手 **持续交流**——目的地变化、同行人、预算松紧、节奏快慢都会在多轮对话中被逐步厘清。  
- **偏好因人而异**：针对不同用户沉淀 **可结构化 / 可更新的偏好画像**（如交通偏好、住宿档次、餐饮禁忌、景点类型、体力与作息、亲子/老人模式等，**具体维度与存储策略见技术方案**），使后续每一版规划 **越来越贴近该用户的心仪选项**。  
- **渐进式打磨**：支持从模糊想法到可执行草案的 **多轮修订**；用户的纠正、勾选与否定均应 **反哺** 后续推荐与生成逻辑，降低模板感与重复劳动。

#### 卖点二：准确性 —「交通住宿不靠编」

- **对标痛点**：通用大模型（如豆包）在旅行场景中易出现 **推荐使用不存在的车次或航班、枢纽车站混淆、酒店信息与真实库存脱节** 等 **事实性错误**，损害信任。  
- **产品原则**：涉及 **飞机航班、列车车次、酒店** 的展示或推荐时，TravelPlan **不以纯模型幻觉充当事实**；应以 **授权数据接口、官方/聚合查询结果或可核验引用** 为唯一可信来源，并在界面层展示 **数据来源、查询时间与跳转核验路径**（具体接入清单与优先级 **待定**）。  
- **无数据时的诚实**：若某一时段无法查到可靠结果，须 **明确标注「未核验」或「暂无实时数据」**，并引导用户至官方渠道核实，**禁止**伪装成已验证事实。  
- **与闭环预订的关系**：准确性目标的达成 **不依赖** 必须在站内完成支付；MVP 可采用 **查询展示 + 外链深链预订**。若阶段内尚无法接入权威交通/住宿数据，则对外传播须 **弱化「准确性」表述**，避免与卖点二冲突。

## 3. 终端与渠道策略（已确认）


| 阶段               | 终端 / 渠道      | 说明                                                                |
| ---------------- | ------------ | ----------------------------------------------------------------- |
| **MVP**          | **Web（浏览器）** | 桌面与移动浏览器均可访问；优先保证 **响应式 / 移动 Web** 可用，以便行前在手机浏览器完成「看地图、改行程、分享链接」。 |
| **迭代（Post-MVP）** | **飞书小程序**    | 面向办公场景渗透与内部分享；账号体系可与飞书身份对接 **[技术方案待定]**。                          |
| **迭代（Post-MVP）** | **微信小程序**    | 面向微信内裂变、分享与支付习惯（若后续商业化）；需遵循各平台审核与地图 SDK 规范 **[技术方案待定]**。          |


**原则**：业务与数据 API **与前端形态解耦**，小程序阶段尽量 **复用同一套后端与行程模型**，避免为小程序重写核心逻辑。

## 4. 范围

### 4.1 MVP（Web）边界

**包含**

1. **行程画布**：按「天」组织 **停留点（POI）**；每个停留点包含名称、时段（可选）、备注；支持 **Web 端拖拽排序**（列表或看板式交互均可，以实现为准）。
2. **地图视图**：日视图或总览上的点与路线示意（具体 SDK：**[待定]** 高德 / Mapbox / Google）。
3. **智能草案**：基于约束（目的地、天数、人群、节奏偏好）生成初稿；输出必须是 **结构化行程**，而非仅聊天文本。
4. **个性化上下文**：支持 **多轮对话** 修订行程；将用户显式表达的偏好 **持久化** 到可引用画像（字段与存储 **待定**），并在后续生成中默认采纳。
5. **交通与住宿事实层**：对 **航班、列车车次、酒店** 提供 **查询结果展示**（来源可追溯）；无数据时 **仅允许「未核验」状态**，不得伪造班次与报价；实现方式可为 API / 聚合搜索 / 外链跳转组合 **[接入方案待定]**。
6. **校验层（差异化核心）**：对草案自动生成 **待核实清单**：如「营业时间未校验」「两点间距过长」「午休缺失（带娃模式）」「交通/住宿未绑定数据源」等规则 **[待定：规则列表]**。
7. **导入（可选 MVP）**：支持粘贴 **纯文本/小红书分享口令或链接** 中的一种 **[待定：先做哪一种]**，解析为候选 POI，用户确认后落格。
8. **分享**：只读链接或导出 PDF/Markdown **[待定]**。
9. **账号与持久化**：行程列表、云端保存 **[待定：是否允许匿名试用]**。

**不包含（MVP 明确不做）**

- **飞书小程序、微信小程序**（列入迭代，见 §4.2）  
- 原生 iOS / Android App（若未来需要，单独立项评估）  
- 站内机酒门票支付与售后  
- 完整离线地图（可做「弱离线：缓存文本行程」**[待定]**）  
- 多人实时协作 OT（若成本高，可先做「分享只读 + 评论」**[待定]**）

### 4.2 迭代规划（Post-MVP，非承诺排期）

- **飞书小程序**：在 Web MVP 核心路径稳定后启动；目标能力对齐「查看 / 轻量编辑行程、分享、接收通知」等 **[范围待定]**。  
- **微信小程序**：在 Web 能力与账号体系稳定后启动；可侧重「分享打开、只读浏览、引导回 Web 深度编辑」或全功能 **[产品决策待定]**。  
- 两人及以上协作编辑、权限与变更记录  
- 与日历同步（ICS）  
- 预算模块与多币种  
- 更强的「实时营业/闭馆」数据源对接

## 6. 用户故事与验收要点

### 6.1 Epic A：创建与编辑行程


| ID    | 用户故事                                    | 验收要点                                               |
| ----- | --------------------------------------- | -------------------------------------------------- |
| US-A1 | 作为 Planner，我希望新建行程并填写目的地与日期范围，以便开始规划。   | 创建后生成默认「Day 1…Day N」骨架；可修改日期范围并联动清空或压缩 **[待定策略]**。 |
| US-A2 | 作为 Planner，我希望在某一天添加/删除/排序停留点，以便贴合真实动线。 | 增删改即时保存；排序后地图顺序一致。                                 |
| US-A3 | 作为 Planner，我希望在地图上看到当天点的位置与顺序，以便判断绕路。   | 地图与列表双向选中一致；显示估算路程时间 **[数据来源待定]**。                 |

| ID    | 用户故事                                          | 验收要点                   |

| US-B1 | 作为 Planner，我希望输入约束后一键生成多日草案，以便节省 Research 时间。 | 生成结果写入结构化行程，而非仅对话框历史。  |
| US-B2 | 作为 Planner，我希望在生成后可整体「重新生成某一天」，以便局部试错。        | 仅替换指定日，其它日不变 **[待定]**。 |

| US-C2 | 作为 Planner，我希望系统提示「动线可能过紧」的天，以便我放宽安排。     | 规则可配置阈值 **[待定表格]**。          |

| ID    | 用户故事                                 | 验收要点                         |

## 7. 功能需求汇总（MoSCoW）


| 需求              | MoSCoW         | 说明                     |
| --------------- | -------------- | ---------------------- |
| 多日行程 + 停留点 CRUD | **Must**       | 核心数据模型                 |
| 地图展示与顺序         | **Must**       | 体验基线                   |
| AI 生成结构化草案      | **Must**       | 与竞品对齐的入门能力             |
| 用户偏好沉淀与多轮对话上下文  | **Must**       | 对应核心卖点「个性化」；持久化策略待定   |
| 航班 / 车次 / 酒店可核验查询与展示 | **Must**       | 对应核心卖点「准确性」；须对接授权数据源或标注未核验 |
| 待核实清单（规则引擎 v0）  | **Must**       | 差异化与信任；与准确性卖点共用一套诚实标注 |
| 账号体系与云端存储       | **Should**     | 视是否匿名试用而定              |
| 外部攻略导入          | **Could**      | 与圆周旅迹竞争相关，但_parser_成本高 |
| PDF 导出          | **Could**      | Plantrip 类需求           |
| 飞书 / 微信小程序      | **Won't（MVP）** | MVP 仅 Web；迭代接入         |
| 多人实时协作          | **Won't（MVP）** | 复杂度控制                  |

## 8. 关键流程（文字版）

1. **新建行程** → 填目的地、天数、偏好 → **生成草案** → 用户拖拽调整
2. 系统生成 **待核实清单** → 用户逐项确认或修改 POI/时间
3. **分享只读链接** → 同伴浏览
4. （可选）**导入笔记** → 解析候选点 → 用户确认落格

## 9. 数据模型（逻辑草案）

**Trip**：id、title、destination、startDate、endDate、ownerId、createdAt…  
**Day**：tripId、date、order…  
**Stop**：dayId、name、lat/lng（可空）、startTime、endTime、note、source（manual | ai | import）、verificationStatus…  

详细 Schema 在技术设计文档中展开 **[Out of PRD scope for v0.4]**。

## 11. 竞品对标与差异化（执行层）


| 维度    | 圆周旅迹 / 豆包 / Mindtrip / Travo / Plantrip | TravelPlan MVP 取向          |
| ----- | --------------------------------------- | -------------------------- |
| 结构化资产 | 强弱不一                                    | **行程对象为一等公民**              |
| 事实校验  | 豆包等对话工具薄弱                               | **交通住宿走授权数据 + 待核实清单 + 用户确认** |
| 闭环预订  | 部分产品强                                   | **MVP 不做支付**，可做跳转 **[待定]** |
| 国内种草  | 圆周旅迹强                                   | **导入可为 Could；规则与解析单独里程碑**  |

## 12. 风险与依赖


| 风险         | 缓解                                             |
| ---------- | ---------------------------------------------- |
| POI/路线数据不准 | 标注「未核实」；对接权威数据源 **[待定]**                       |
| 大模型幻觉      | 结构化输出 + JSON Schema 校验；**航班/车次/酒店不经模型臆造** |
| 交通住宿数据接入成本与合规 | 优先对接国内可用 API / OTA 聚合；合同与调用配额前置评审 **[待定]** |
| 导入侵权与解析稳定性 | MVP 可降级为手动粘贴标题列表                               |

## 13. 开放问题（需产品评审）

1. ~~**首发形态**~~：**已定为 MVP Web**；迭代增加 **飞书小程序、微信小程序**（见 §3、§4.2）。  
2. **MVP 是否包含「攻略导入」**：若包含，先做链接还是文本？
3. **地图与 POI 供应商**：国内优先高德？
4. **商业化**：免费 + 订阅 / 按次 AI / B 端？ **[本版 PRD 不写定价]**
5. **隐私**：行程是否默认私密；分享链接有效期？
6. **小程序迭代优先级**：飞书与微信 **谁先开发**、小程序是否只做「只读 + 跳转 Web」还是功能对等？
